# Роадмап: ИИ-сотрудники через API — от симулятора к живому магазину

*Как поэтапно замещать отдельные роли магазина ИИ-агентами, работающими
«как обычные сотрудники», — по той же логике уровней автономии, по
которой индустрия прошла путь к робо-такси.*

---

## Идея

Командный тренажёр planogram3d уже сегодня устроен так, что **роль не
знает, кто её исполняет**: человек в браузере, встроенный бот и внешний
ИИ подключаются к смене одним и тем же контрактом
`join → state → action`. Это и есть ключ к замещению: если агент
надёжно исполняет роль в симуляторе на цифровом двойнике магазина, тот
же контракт можно вывести на живые системы — сначала в теневом режиме,
затем с надзором, затем автономно. Ровно так робо-такси прошло путь от
полигона к коммерческим перевозкам: **симулятор → теневой режим →
оператор в контуре → автономия в ограниченной зоне → масштабирование**.

## Уровни автономии роли (по аналогии с SAE для транспорта)

| Уровень | Название | Кто работает | Аналог в такси |
|---|---|---|---|
| **A0** | Только человек | человек без подсказок | обычный водитель |
| **A1** | Ассистент | человек + подсказки ИИ («полка 2 пустеет», «очередь растёт») | круиз-контроль |
| **A2** | Второй пилот в симуляторе | человек учится рядом с ботами в тренажёре | автопилот на трассе под присмотром |
| **A3** | Автономия в симуляторе | ИИ полностью ведёт роль в цифровом двойнике | беспилотник на полигоне |
| **A4** | Теневой режим и надзор в живой системе | ИИ читает реальные потоки данных, решения исполняются после подтверждения человеком; затем — сам, человек наблюдает | робо-такси с оператором |
| **A5** | Автономная роль | ИИ исполняет роль в живой системе; человек — только эскалации | робо-такси без водителя |

**Сегодня система находится на A3**: встроенные боты и внешние агенты
(`/api/mgame/...`) полноценно работают во всех пяти ролях командной
смены, эталонный агент — `webapp/tools/demo_bot.py`.

## Какие роли замещаются и в каком порядке

Принцип очерёдности: **цифровые роли раньше физических**. Роли, чья
работа — решения и данные, автоматизируются существующими API; роли с
физическим трудом требуют робототехники и уходят в конец роадмапа.

| Роль | Что делает ИИ | Уже есть в системе | Целевой уровень |
|---|---|---|---|
| Диспетчер доставки | группировка заказов, маршруты, контроль плана на Ганте, переназначение при опоздании | конвейер `/api/delivery/*`, Гант, GPS-телеметрия | **A5** — полностью цифровая роль |
| Менеджер пополнения | заказ в РЦ по прогнозу, а не по факту OOS; приоритизация рейсов | автозаказ при OOS, склад РЦ, перезаказ поставщикам | **A5** |
| Техник-мониторинг | реакция на тревоги ХВ, ленту, оборудование: заявка/перезапуск до выезда человека | Zabbix-интеграция, события `fridge`, расходники | **A4→A5** (физическая замена ленты остаётся человеку/роботу) |
| Супервайзер смены | балансировка: кого куда направить, открыть вторую кассу, вызвать уборку | роль supervisor в mgame, все датчики зала | **A4** — рекомендации людям, исполнение смешанное |
| Кассир | СКО — уже «автономная касса»; штатная касса — ассистент скорости/подсказок | зона СКО в симуляции и зале | **A2 на штатной, A5 на СКО** |
| Клинер / мерчандайзер | физический труд: робот-уборщик, робот-выкладчик | политика в симуляторе | **A3 в симуляторе**, A4+ по мере зрелости робототехники |

## Дорожная карта

### Фаза 0 — сделано (A3 в симуляторе)

* Единый контракт агента `join / state / action`, комнаты-сессии,
  лимиты ролей, смешанные смены человек+ИИ.
* Эталонные политики всех пяти ролей, внешний агент по REST.
* Метрики вклада и баллов — базовая система оценки агентов.

### Фаза 1 — симулятор как полигон агентов (кв. 1)

* **Стандарт Agent API v1**: версионированный JSON-контракт состояния и
  действий, одинаковый для симулятора и (в будущем) живых систем;
  токены агентов, rate-limit.
* **Сид-режим и повторяемость**: фиксированный сценарий смены для
  честного сравнения агентов (лиги, регрессионные прогоны).
* **Экзамен роли** — как лицензирование робо-такси: агент допускается
  дальше, только если на N сменах держит KPI (очередь ≤ X, OOS-время
  ≤ Y, потерянные покупатели ≤ Z) не хуже эталона и без «аварий»
  (грубых нарушений регламента).
* Хакатоны студентов: соревнование агентов на одинаковом сиде.

### Фаза 2 — теневой режим в живой системе (кв. 2–3, A4)

* Подключение агентов к **реальным потокам**, которые система уже
  принимает: события касс/CCTV (`/api/instore/ingest`), телеметрия
  холодильников, Zabbix, GPS доставки.
* Агент **предлагает, человек исполняет**: рекомендации («открой кассу
  2», «закажи пополнение сейчас, к 18:00 будет OOS») попадают в ленту
  супервайзера; каждая рекомендация логируется вместе с решением
  человека — это же и датасет для дообучения.
* Метрика качества тени: доля рекомендаций, принятых людьми; ущерб,
  предотвращённый принятыми.

### Фаза 3 — надзорная автономия цифровых ролей (кв. 3–4, A4→A5)

* **Диспетчер доставки** и **менеджер пополнения** переходят на
  автономное исполнение: агент сам строит маршруты и размещает заказы
  в РЦ; человек видит план и имеет «красную кнопку».
* Границы полномочий (guardrails): лимиты сумм заказа, радиус
  маршрута, запрещённые действия; всё сверх лимита — эскалация.
* Канареечный запуск: один магазин / один маршрут в день, сравнение
  KPI с человеческой базой, автоматический откат при деградации.

### Фаза 4 — автономные цифровые роли в проде (год+, A5)

* Диспетчеризация, пополнение и мониторинг работают без человека в
  контуре; человек — только эскалации и аудит.
* Агент проходит переэкзаменовку при каждом изменении модели (как
  переаттестация парка робо-такси после обновления автопилота).
* Пул агентов от разных команд/вендоров конкурирует на одинаковых KPI
  — симулятор остаётся общим полигоном допуска.

### Фаза 5 — физические роли (горизонт)

* Интеграция роботов-уборщиков (рынок уже зрелый) в роль «клинер»:
  тот же Agent API, исполнителем действия `clean` становится робот.
* Робот-выкладчик для мерчандайзинга — по мере зрелости технологий;
  до того ИИ-мерчандайзер работает в паре с человеком: планирует,
  человек исполняет (A4).

## Технические принципы (неизменные на всех фазах)

1. **Один контракт — много исполнителей.** Роль описана API, а не
   типом исполнителя; человек, бот, внешний ИИ и робот взаимозаменяемы.
2. **Симулятор — обязательный полигон.** Ни один агент не касается
   живой системы, не сдав «экзамен роли» в цифровом двойнике; сам
   двойник постоянно калибруется реальными потоками данных.
3. **Ступенчатое доверие.** Подсказка → рекомендация с подтверждением
   → автономия с надзором → автономия. Переход только по метрикам,
   откат — автоматический.
4. **Человек в контуре по построению.** Эскалации, «красная кнопка» и
   журналирование каждого решения агента — часть контракта, а не
   опция.
5. **Обучение не останавливается.** Логи теневого режима и живой
   работы возвращаются в симулятор как сценарии; смены с людьми дают
   агентам примеры, агенты дают людям эталон — цикл, знакомый по
   автопилотам.

## Ближайшие практические шаги

1. Зафиксировать Agent API v1 (схема JSON, токены, версия в URL).
2. Добавить сид-режим и прогон «экзамена роли» в CI.
3. Провести первый хакатон агентов на эталонном сиде.
4. Выбрать пилотный магазин для теневого режима диспетчера доставки.
