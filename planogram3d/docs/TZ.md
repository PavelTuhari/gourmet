# Техническое задание — модуль planogram3d

*Версия 1.1 · 16.08.2026 · статус: реализовано и проверено запуском
(п. 12 — принятые изменения последней ревизии).*

## 1. Назначение

Самодельный 3D-модуль для ERP торговой сети «Гурман» (Тверь):
цифровой двойник сети — от планограммы полки до города, включая
логистику, датчики торгового зала, игровой тренажёр персонала и
интернет-доставку с ИИ-прогнозом прибытия.

## 2. Состав системы (функциональные требования)

### 2.1. Ядро планограмм (`core/`)

* Модель данных магазина (dataclasses, без внешних зависимостей):
  товары, поставщики, контракты, стеллажи/полки, планограмма,
  продажи, регламент.
* 3D-визуализация выкладки (plotly): режимы «текущее состояние
  продаж» и «утверждённая планограмма», цветовой код остатков.
* Движок проверки соответствия: внутренний регламент, контракты
  с поставщиками, план-факт против утверждённой планограммы,
  аномалии продаж; расширяем пользовательскими правилами.
* Отчёты: консоль, HTML-блок, автономная HTML-страница.
* Все данные заходят только через объект `Store` — интеграция с любой
  учётной системой сводится к его наполнению.

### 2.2. Карта сети (веб, `/`)

* Автономная карта города (MapLibre + GeoJSON в репозитории,
  интернет не требуется), режимы 2D и 3D (этажность зданий).
* Эмуляция торгового дня (1 с = 10 мин): продажи, выручка,
  out-of-stock, пополнения, лента событий, уровень магазина 1–5★.
* Логистический центр (РЦ): склад, точка перезаказа, отгрузки
  грузовиками **по реальным дорогам города** (маршрутизация A* по
  графу OSM), прямые поставки поставщиков.
* Мониторинг Zabbix: бейджи активных проблем на маркерах
  (реальный API либо эмулятор с тем же интерфейсом).
* Вход в магазин с карты: планограмма / симуляция зала / тренажёр.

### 2.3. Симуляция торгового зала (`/store/<id>/live`)

Очереди на кассах и СКО, ТСД (BLE/LoRa), холодильники с температурой,
расходники, скоропорт, оценка трафика по датчикам входа/выхода;
реальный поток событий — `POST /api/instore/<id>/ingest`
(глушит эмулятор по таймауту 60 с).

### 2.4. Тренажёр персонала (`/store/<id>/game`, `/game/multi`)

Соло-смены (3 уровня) и командная смена до 10 участников с ролями;
сервер авторитарен, роль не знает, кто её исполняет — человек,
встроенный ИИ-бот или внешний ИИ-агент по REST API. Баллы и бейджи
уходят в Roblox-хаб команды (Open Cloud или эмулятор).

### 2.5. Интернет-заказы и доставка (`/delivery`)

* Конвейер: заказ → сборка по планограмме → маршрут (2–4 адреса,
  ближайший сосед) → курьер → вручение.
* Движение курьеров по дорогам города; GPS-телеметрия реального
  курьерского приложения (`POST /api/delivery/gps`) глушит эмуляцию.
* Диаграмма Ганта план/факт по каждому плечу.
* Чеки 54-ФЗ в момент вручения: облачная касса (Android) или
  SmartPOS с ФН на борту; печатная форма `GET /receipt/<id>`.

### 2.6. Онлайн-табло прибытия с ИИ-прогнозом (новое, v1.1)

По аналогии с «умными остановками» городского транспорта
(GPS-телеметрия → ИИ-модель → электронное табло; референс — проект
Urban Way, Бельцы, EIT Urban Mobility):

* **Каждый пункт доставки** видит на карте онлайн-табло времени
  прибытия транспорта:
  * магазин — машины поставщиков и РЦ (карточка магазина на карте
    сети, блок «🚏 Табло прибытия · ИИ»);
  * адрес покупателя — курьер, позиция в очереди маршрута
    (клик по точке на `/delivery`, живое обновление попапа).
* **Время просчитывается ИИ**: онлайн-обучаемая модель
  (`webapp/eta_ai.py`) без внешних зависимостей:
  * EWMA-оценки фактической скорости и её дисперсии по классам
    транспорта (грузовик / курьер), дообучение на телеметрии каждого
    завершённого плеча (метры по дорожному графу × секунды);
  * обучаемые коэффициенты трафика по часу суток (часы пик модель
    выучивает сама — в эмуляции трафик замедляет рейсы в пики);
  * прогноз длительности вручения заказа (EWMA);
  * выдача: время прибытия, неопределённость ±1σ (копится по плечам),
    плановое время для сравнения, число наблюдений в модели.
* API: `GET /api/eta/store/<store_id>`, `GET /api/eta/order/<order_id>`;
  прогнозы также добавляются в остановки `GET /api/delivery/state`
  (`ai_arrive`, `ai_sigma`, `ai_note`).
* Одна модель на процесс: рейсы РЦ и курьеров учат общий прогнозист;
  реальная GPS-телеметрия участвует в обучении наравне с эмуляцией.

### 2.7. Roblox-контур

Конвертер сцен в `.rbxlx` (собственный писатель формата, без
зависимостей) + Luau-тренажёр; баллы/бейджи команды через Open Cloud
или эмулятор.

### 2.8. Документация и презентация

Живая документация внутри системы (`/docs/`), HTML-презентация с
BPMN-диаграммами и ссылками в работающее демо (`/presentation`),
pptx-версия, методичка (HTML генерируется из MD скриптом
`webapp/tools/build_article_html.py`).

## 3. Нефункциональные требования

| Требование | Решение |
|---|---|
| Автономность | карта, шрифты, библиотеки — в репозитории; интернет не нужен |
| Зависимости | ядро — только plotly; веб — plotly + flask; десктоп — + pywebview |
| Платформы | веб (`python3 -m planogram3d.webapp`), нативное окно macOS/Linux (`planogram3d.desktop`, pywebview), `.app`-бандл для двойного клика |
| Архитектура симуляций | evolve-on-poll, без лишних фоновых потоков (исключение — тикер сети, 2 с) |
| Внешние контуры | у каждого — эмулятор с интерфейсом реального источника; реальный поток глушит эмулятор по таймауту |
| ИИ-прогноз ETA | онлайн-обучение в процессе, без внешних ML-зависимостей; потокобезопасность (lock) |
| Хранение | всё состояние в памяти процесса (демо-система); реестр команды — JSON-файл |

## 4. Критерии приёмки (все проверены запуском)

1. `GET /api/state`, `/api/instore/st17/state`, `/api/delivery/state`,
   `/api/roblox/team` → 200 с живыми данными.
2. Грузовики и курьеры двигаются по полилиниям улиц (не по прямым).
3. Клик по маркеру магазина открывает карточку с табло прибытия;
   у машин в пути — ИИ-время, ±σ и источник прогноза.
4. Клик по точке доставки открывает попап-табло с очередью курьера;
   табло обновляется каждые ~1.5 с без закрытия.
5. `GET /api/eta/store/st17` и `/api/eta/order/<id>` отдают прогнозы
   и сводку модели; после нескольких завершённых рейсов `obs > 0`
   и скорость отличается от априорной (модель учится).
6. Чек `GET /receipt/<id>` открывается из ленты чеков.
7. Нативное окно (`Planogram3D.app`) открывается двойным кликом и не
   оставляет процессов после закрытия.
