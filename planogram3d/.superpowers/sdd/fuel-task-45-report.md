# Отчёт: Задачи 4 и 5 плана PLAN_FUEL_AUTOORDER.md

Ветка `claude/3d-sales-visualization-fsbyam` (уже была выбрана, новых не создавал).

## Что сделано

### Задача 4 — маршруты сервера

- `webapp/server.py`: импорт и модульный синглтон `fuel = FuelNetwork()`
  рядом с `network`, `delivery`, ... Добавлены маршруты:
  - `GET /fuel` → `render_template("fuel.html")`
  - `GET /api/fuel/state` → `jsonify(fuel.state())`
  - `GET /api/eta/fuel/<station_id>` → `jsonify(fuel.arrival_board(station_id))`,
    404 если станции нет.
- `webapp/peco_fuel.py`: добавлен метод `FuelNetwork.arrival_board(station_id)`.
  По архитектуре проекта (`network.arrival_board`, `delivery.arrival_board`)
  бизнес-логика табло живёт в контуре, а не в `server.py` — маршрут
  тонкий. Форма ответа: `{"now", "point", "station_id", "source", "rows", "model"}`,
  строка `rows[i]` — `{type, icon, label, eta_sec, sigma_sec, eta_ts,
  plan_ts, progress, source}`, что совпадает с полями, которые уже
  использует фронтенд табло на `/delivery` (`icon`, `eta_ts`, `sigma_sec`,
  `plan_ts`, `source`). Прогноз строится через `eta_ai.get_predictor()
  .predict("tanker", remaining_m)`, `remaining_m` — расстояние по прямой
  от текущей позиции бензовоза до станции с коэффициентом ×1.25 на
  извилистость дороги (тот же приём, что уже применён в
  `delivery._ai_stop_predictions` для плеча без точного дорожного остатка).

### Задача 5 — карта топливной сети

- `webapp/templates/fuel.html` (новый файл): MapLibre-карта Молдовы,
  источник `/static/data/moldova_map.geojson`, старт zoom 7, центр
  `[28.6, 47.0]`. Слои: `water`, `road`, `road_major` (стиль в духе
  `map.html`), `places` (кружки городов — см. «отклонения»),
  `routelines` (полилинии рейсов). Нефтебаза — маркер 🏭, 46 АЗС —
  круглые маркеры, окрашенные по остатку (зелёный/жёлтый/красный) с
  подписью процента заполненности прямо на маркере — это главный
  сигнал экрана, как и требовало задание. Клик по АЗС вызывает
  `showEtaBoard(stationId, lon, lat)` — попап `🚏 Табло прибытия · ИИ`,
  тот же HTML/CSS-контракт, что в `delivery.html` (класс `.eta-board`,
  живое обновление открытого попапа на каждом опросе). Боковая панель:
  список рейсов с прогресс-баром, прогоны автозаказа, лента событий,
  индикатор источника (эмуляция/Artgranit), ссылка `← карта сети` на `/`.

### Визуальная проверка Задачи 5

Инструмент: встроенный Browser pane (`preview_start` + `computer`
screenshot + `javascript_tool`), реальный запущенный сервер на 8051.
Не имитация — реальный рендеринг MapLibre в браузере.

1. Первый скриншот `/fuel` — карта пустая (только сайдбар и легенда,
   без дорог/воды/маркеров). `read_console_messages` вскрыл причину:
   `layers[4].layout.text-field: use of "text-field" requires a style
   "glyphs" property`. Я добавил в стиль слой `places` типа `symbol`
   с `text-field` для подписи городов, но MapLibre **не рендерит
   вообще никакой слой стиля**, если хоть один слой ссылается на
   `glyphs`, а свойство `glyphs` в стиле не задано (а задавать его
   нельзя — это внешний сервер шрифтов, карта обязана быть
   автономной). Это не «мелкая деталь подписи», а полный обрыв рендера
   всей карты — нашёл именно потому, что посмотрел на скриншот, а не
   поверил коду.
2. Исправил: слой `places` — `type: "circle"` вместо `symbol`,
   подписи городов убраны (в `map.html` для Твери такого слоя нет
   вовсе — не изобретал новый паттерн, просто не стал городить подписи
   без глифов).
3. Сервер Flask по умолчанию кэширует Jinja-шаблоны без
   `TEMPLATES_AUTO_RELOAD` — после правки файла пришлось перезапустить
   процесс (не просто hard-reload в браузере), иначе `/fuel` продолжал
   отдавать старый HTML. Проверил через `curl | grep`, что отданный
   HTML действительно обновился, только потом полез в браузер снова.
4. После перезапуска и `map.resize()` (после смены размера окна)
   получил корректный рендер: `map.getStyle().layers` →
   `["bg","water","road","road-major","places","routelines"]`,
   `map.loaded() === true`, ошибок в консоли для актуальной загрузки
   не было (старые записи о `text-field` остались в буфере логов от
   предыдущей навигации — не относятся к текущему состоянию, что я
   перепроверил через `map.getStyle()` напрямую).
5. Смотрел на итоговые скриншоты (900×650 и 736×532, реальные пиксели,
   не описание): видно жёлто-бежевые линии `road_major`, серые/белые
   тонкие `road`, кружки станций, окрашенные зелёным/жёлтым/красным с
   числом «NN%» прямо на маркере, тёмно-зелёные значки бензовозов
   (грузовик-эмодзи) **сидящие прямо на пунктирной фиолетовой линии
   маршрута**, а не в стороне от неё — то есть рейс действительно едет
   по трассе, а не по прямой. `document.querySelectorAll('.st-mark')
   .length === 46` — все станции есть в DOM (часть визуально
   накладывается друг на друга в кластерах городов при зуме 7 — это
   ожидаемо: у нескольких городов по 2–4 станции с почти одинаковыми
   координатами).
6. Клик по маркеру АЗС в живой, быстро эволюционирующей эмуляции
   (TIME_SCALE=2400, опрос раз в 1.5 с) физически промахивался мимо
   маркера между снятием координат и кликом — сами маркеры двигаются.
   Чтобы не подменять проверку — вызвал ровно ту же функцию
   `showEtaBoard(stationId, lon, lat)`, которую вызывает `onclick`
   обработчика маркера (код идентичен паттерну `delivery.html`), через
   `javascript_tool`. Получил и увидел на скриншоте реальный попап:
   заголовок «🚏 Табло прибытия ИИ», подзаголовок «АЗС №3 Орхей»,
   строка `FT-0012 · Ион Гуцу · 7500 л`, время прибытия, `±4 с`, план
   `11:07`, источник «ИИ-прогноз (модель обучена, 23 рейс.)» — попап
   затем сам обновился на следующих опросах (живое обновление
   подтверждено визуально: время в попапе менялось между скриншотами
   без повторного клика).
7. `map.getBounds()` вернул `{sw: {lng:26.95, lat:45.86}, ne:
   {lng:30.25, lat:48.12}}` при `zoom:7, center:[28.6,47]` — это
   покрывает полный охват станций PECO (27.30–29.42 / 45.89–48.17), то
   есть карта показывает всю Молдову, а не обрезанный кусок.

Итог визуальной проверки: не пустой холст, станции не в одной точке —
разбросаны по стране кластерами по городам (что соответствует реальным
координатам PECO), бензовоз стоит на линии трассы, табло открывается и
живо обновляется. Проверка прошла, но с находкой и правкой бага
(glyphs), а не «с первого раза всё идеально».

## Отклонения от буквы задания и сомнения

1. **Файл, который правил, шире списка "Файлы" Задачи 4.** План
   указывал для Задачи 4 только `webapp/server.py`, но чтобы не ломать
   архитектурный инвариант проекта (бизнес-логика табло — в контуре,
   `server.py` — тонкий диспетчер, как у `network.arrival_board` /
   `delivery.arrival_board`), метод `arrival_board` я добавил в
   `webapp/peco_fuel.py`. Считаю это правильным следованием стилю
   кодовой базы, а не расширением задания, но фиксирую как осознанное
   отклонение от буквы карты файлов.
2. **ETA по прямой ×1.25, а не по точному дорожному остатку.** Для
   реального потока Artgranit кумулятивные расстояния по маршруту не
   хранятся в публичной форме рейса (`state()["trips"]`), поэтому для
   табло я использовал прямое расстояние с тем же коэффициентом
   извилистости, что уже применяется в `delivery.py` для аналогичного
   случая (плечо без точного дорожного остатка). Для эмуляции это
   немного менее точно, чем взять `stop["cum_dist"] - trip["leg_pos"]`
   из внутреннего состояния, но даёт единый код для обоих режимов
   (эмуляция/Artgranit) без дублирования логики раскрутки маршрута.
   Если для табло критична именно дорожная точность в режиме
   эмуляции — можно уточнить отдельным патчем.
3. **Подписи городов на карте не буквенные, а точки.** Формально план
   говорит, что у `place` есть `name` и `rank`, подразумевая
   визуализацию; я оставил только кружки без текста, потому что
   `text-field` требует `glyphs` (внешний сервер шрифтов), а это прямо
   запрещено инвариантом автономности карты. `map.html` (тверская
   карта) вообще не имеет слоя `place` — прецедента подписей в проекте
   нет. Название города можно добавить позже DOM-маркерами (как
   `courier-tag` в `delivery.html`), если оно действительно нужно —
   не стал усложнять без явного запроса.
4. **Не проверял живой Artgranit (Задача 6, вне рамок этого захода).**
   Первый раз, когда клиент Artgranit был проверен в предыдущей сессии
   (Задача 3), но в этом заходе я не поднимал сам Artgranit — задание
   ограничивалось Задачами 4–5. `state()["source"]` в проверке оставался
   `"emulation"`, что ожидаемо без `ARTGRANIT_URL`.
5. Сквозной e2e с реальной инициацией автозаказа в Artgranit
   (`POST /api/plg/fuel/autoorder`) — это Задача 6 плана, не входила в
   этот заход, не выполнялась.
