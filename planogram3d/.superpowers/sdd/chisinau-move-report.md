Симуляция здесь evolve-on-poll (§ инвариантов CLAUDE.md), поэтому
маршруты появляются не сразу после одного опроса — опрашивал
`/api/delivery/state` несколько раз подряд (в сумме ~2 минуты реального
времени с несколькими последовательными `curl`), пока не набралось
достаточно упакованных заказов для сборки маршрута. Ошибок в

## Отклонения и сомнения

- Задержка появления первого маршрута (потребовалось несколько
  последовательных опросов `/api/delivery/state` вместо одного
  `sleep 25; curl` как в шаблоне задачи) — не баг переноса, а следствие
  evolve-on-poll модели: сборка заказа (`picking → packed`) и группировка
  в маршрут завершаются по реальному времени, но полностью зависят от
  частоты вызовов `/api/delivery/state` (маршруты собираются только
  внутри `state()`). Это существующее поведение системы, не связанное
  с переносом города — с тверскими координатами вело бы себя так же.
  Просто первый прогон с одним `sleep 25` не попал в нужное окно.
- Часть кода в `webapp/peco_fuel.py` содержит слово «тверская» только
  как объяснение архитектурного решения (почему там не используется
  общий синглтон широты) — оставил как есть согласно прямому запрету
  трогать топливный контур; при желании эти строки можно переформулировать
  отдельным мелким PR, но по букве задачи это уже не про «убрать Тверь
  из работающей системы», а про причёсывание комментариев в модуле,
  который просили не трогать.
- `tver_map.geojson` не удалён (по требованию задачи) — физически
  всё ещё лежит в репозитории, 2.1 МБ мёртвого веса; решение — за
  владельцем.
