# Задача 3: реальный поток из Artgranit — отчёт

## Что сделано

`webapp/peco_fuel.py` дополнен живым опросом Artgranit по образцу
`REAL_GPS_TIMEOUT` из `webapp/delivery.py`:

* `ArtgranitClient` — тонкий HTTP-клиент только на чтение
  (`GET /api/plg/fuel/stations`, `GET /api/plg/fuel/trips`), без
  зависимостей сверх `urllib`/`json`/`email.utils` из стандартной
  библиотеки. Любая ошибка (`success != true`, не-200, разрыв сети,
  таймаут, битый JSON) поднимается как исключение и ловится вызывающей
  стороной — наружу не просачивается.
* `FuelNetwork` создаёт клиента только если задана переменная
  `ARTGRANIT_URL` — без неё контур не делает ни одного сетевого вызова,
  автономность по умолчанию сохранена.
* Опрос вписан в `state()` (`_poll_artgranit`), без фонового потока:
  не чаще `ARTGRANIT_POLL_INTERVAL` секунд, результат кладётся в кэш
  `self._real_cache` вместе с меткой времени `self._last_real`.
* `state()` считает данные «реальными» (`source: "artgranit"`), пока
  `now - self._last_real < REAL_ARTGRANIT_TIMEOUT`; как только окно
  истекло — контур сам возвращается к `"emulation"`, ничего не роняя.
  Переходы источника логируются в ленту событий (`events`) один раз, а
  не на каждый неудачный опрос.
* Эмулятор продолжает считать своё состояние (`_consume`,
  `_maybe_dispatch`, `_evolve_trips`) независимо от режима отдачи —
  ровно так же, как задумано в шапке модуля («эмулятор работает
  всегда»); просто наружу при живом Artgranit уходит не он, а
  преобразованные реальные данные.

### Преобразование форм Artgranit → форма контура

* Станции: прямое переложение полей (`station_id → id`,
  `daily_rate_l`, `capacity_l`, `current_l` → `fill_pct`,
  `days_to_dry`, `is_low` — та же арифметика, что у эмулятора).
* Рейсы (`_trip_from_artgranit`):
  * учитываются только `status == "en_route"` и недавно завершённые
    `"done"` (окно `DONE_TRIP_RETENTION_S = 90` с, как у эмулятора);
    `"planned"` рейсы (ещё не выехали) на карту не попадают;
  * реальный `GET /trips` отдаёт остановки построчно по **отсекам
    цистерны** — несколько строк с одинаковым `station_id` это разные
    секции одной физической остановки, а не разные заезды; код
    группирует их по `station_id`, суммируя `liters_fact`/`liters_plan`;
  * маршрут и полилиния строятся нашим `RoadNet` по молдавской карте
    (депо → остановки в порядке появления), т.к. свой путь Artgranit
    не отдаёт (подтверждено на живых данных: поля `path`/`polyline` в
    ответе нет);
  * `last_lat`/`last_lon` действительно `null` на всех проверенных
    рейсах (GPS-провайдер не подключён, как и предупреждал план) — в
    этом случае позиция считается по маршруту и доле пройденного
    планового времени (`(now - depart) / (eta - depart)`,
    `point_along` по полилинии), как и в эмуляции. Код читает
    `last_lat`/`last_lon`, когда они всё же есть, и тогда считает
    прогресс по фактическому пройденному расстоянию от нефтебазы.
  * даты — `email.utils.parsedate_to_datetime`, как предписано (свой
    парсер не писался).
* Координаты нефтебазы Artgranit не отдаёт ни в одном осмотренном
  эндпоинте — как и в эмуляторе, используются зашитые в модуль
  координаты пос. Сынжера (`DEPOT_LAT`/`DEPOT_LON`), это уже было
  задокументировано в модуле при Задаче 2.

## Проверка (Шаг 2 плана), фактический вывод

Обе команды выполнены как в задании, без изменений:

```
=== 1) ARTGRANIT_URL=http://127.0.0.1:3003 ===
источник: artgranit станций: 46 рейсов: 3

=== 2) ARTGRANIT_URL=http://127.0.0.1:59999 (недоступен) ===
источник (недоступный Artgranit): emulation станций: 46
```

Ни разу не возникло исключения ни в первом (реальный сервер отвечает),
ни во втором случае (адрес недоступен: `ConnectionRefusedError` внутри
`urllib` ловится, `state()` тихо остаётся на эмуляции).

Дополнительно (для собственной проверки качества данных, не входит в
обязательный вывод плана) прогнан детальный дамп `trips` в режиме
`artgranit` — все 3 попавших в выдачу рейса имеют многоузловые
полилинии, построенные `RoadNet` (322 и 1037 узлов), реальные координаты
станций назначения и суммированные по отсекам литры. Замечено: у двух
рейсов (`AG-13`, `AG-9`) прогресс вышел `1.0` (труба «доехала») — это
не ошибка преобразования, а следствие того, что часы демо-сценария
Artgranit (`plan_arrive` в районе 05:08 GMT 20.08.2026) относительно
реального времени машины уже в прошлом на момент проверки; на
интеграцию это не влияет, при живом опросе после `POST
/fuel/trips/plan` свежий рейс получит корректный прогресс от 0.

## Переменные окружения (добавлены, задокументированы в `docs/HANDOFF.md` §6)

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `ARTGRANIT_URL` | не задана | адрес ERP; не задана → контур полностью автономен, клиент не создаётся |
| `ARTGRANIT_TIMEOUT` | `3.0` (с) | таймаут одного GET-запроса |
| `ARTGRANIT_POLL_INTERVAL` | `5.0` (с) | минимальный интервал между опросами (evolve-on-poll) |
| `REAL_ARTGRANIT_TIMEOUT` | `20.0` (с) | окно свежести реальных данных; истекло — возврат к эмуляции |

## Как устроен возврат к эмуляции по таймауту

Приём один в один с `REAL_GPS_TIMEOUT` из `delivery.py`, только на
уровне всего контура, а не отдельного курьера:

1. `_poll_artgranit(now)` — не чаще `ARTGRANIT_POLL_INTERVAL`; при
   успехе пишет `self._real_cache` (готовые к отдаче `stations`/`trips`)
   и `self._last_real = now`.
2. `state()` вычисляет `is_real = self._real_cache is not None and
   now - self._last_real < REAL_ARTGRANIT_TIMEOUT`.
3. Пока `is_real` — наружу уходит кэш реальных данных,
   `source = "artgranit"`.
4. Как только время между последним успешным опросом и текущим
   моментом превысило `REAL_ARTGRANIT_TIMEOUT` (Artgranit не отвечает
   несколько опросов подряд, либо выключен), `is_real` становится
   `False` и `state()` проваливается в старый эмуляторный хвост функции
   (`source = "emulation"`) — тот же код, что был до Задачи 3, не
   тронут ни строкой. Никакой отдельной логики «выключения» не нужно:
   эмулятор всё это время продолжал считать своё состояние параллельно,
   так что переключение мгновенно и без скачков (станции/рейсы на
   месте, а не пустой экран).

## Сомнения

* Реальные `plan_arrive`/`act_depart` рейсов Artgranit не всегда
  синхронны с текущим временем машины, на которой крутится
  planogram3d (демо-сценарий ERP может быть «в будущем» или «в
  прошлом» относительно wall-clock) — прогресс рейса на экране может
  на старте показать 0 или сразу 1.0 вместо плавного движения, пока
  Artgranit не проведёт новый рейс с плановым временем, реально
  синхронным с текущим моментом. Это ограничение исходных данных, не
  дефект преобразования.
* Полноценная сквозная проверка «инициация автозаказа в Artgranit →
  появление рейса на экране» — предмет Задачи 6 плана, в рамках Задачи
  3 не выполнялась (Artgranit не пишется, только читается).
