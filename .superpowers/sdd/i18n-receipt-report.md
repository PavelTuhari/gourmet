# Отчёт: механизм локализации (ru/ro/en) + фискальный чек Молдовы

Ветка `claude/3d-sales-visualization-fsbyam`, без новых веток.

## 1. Механизм локализации — `webapp/i18n.py`

Своя реализация без внешних зависимостей (в проекте их принципиально
нет — см. `docs/HANDOFF.md` §3.8, мини-Markdown вместо библиотеки).
Каталог — обычный `dict`, ключи с точечной группировкой по разделу
(`receipt.total`, `log.route_built`), пополняется без тулчейна и без
сборки .po/.mo.

**Нормализация языка** — `normalize_lang(code)`: код обрезается до двух
символов, приводится к нижнему регистру; неизвестный/пустой →
`'ru'`. Контракт умышленно такой же, как у прочих нормализаторов
проекта (id магазина/роли и т.п.) — тихий откат, а не 400/500.

**Множественное число** — ключевая часть задачи. Формы хранятся списком
`MESSAGES[key][lang] = [форма0, форма1, ...]`, индекс формы выбирает
функция для конкретного языка:

* `ru` — 3 формы (алгоритм тот же, что в стандартных реализациях CLDR
  для русского): `n%10==1 and n%100!=11` → форма 0 («заказ»);
  `2<=n%10<=4 and not 12<=n%100<=14` → форма 1 («заказа»); иначе форма 2
  («заказов»). Проверено на 1, 2, 5, 11, 21, 22, 25, 101, 111 вручную по
  таблице правил — совпадает с ожидаемым русским словоизменением.
* `ro` — 2 формы, но с особым правилом CLDR для румынского: числа,
  оканчивающиеся на 01–19 (в том числе после сотен — 101, 119, 219),
  используют ту же форму, что единица, а не «форму по умолчанию»:
  `n==1 or 1<=n%100<=19` → форма 0, иначе форма 1. Это отдельно
  прописано в докстринге `_plural_ro`, чтобы не потерялось при
  пополнении каталога.
* `en` — 2 формы, обычное `n==1` / иначе.

Выбор формы и подстановка параметров объединены в `t(lang, key,
count=None, **params)`: если `count` задан и значение ключа — список,
берётся нужная форма, затем делается `str.format(**params, n=count)`.
Отсутствующий ключ не роняет страницу — возвращается сам ключ (видимая
дыра в каталоге лучше, чем 500-я ошибка).

**Эмодзи вне переводимых строк** — например, `APP_TITLES` в
`delivery.py` (`"📱 Android (облачная касса)"`) не тронут переводом
(эмодзи там завязаны на приложение курьера, а не на язык чека), а в
самом каталоге эмодзи нигде не хранится: где перевод используется в
шаблоне/логе, эмодзи добавляется рядом с вызовом `t(...)`, а не внутри
строки (см. `receipt.html`: `🖨 <span>{{ lbl.print_button }}</span>`,
`delivery.py`: `"🗺 " + i18n_t(...)`).

**Демонстрация механизма на существующем костыле.** В `delivery.py`
была типичная заглушка множественного числа: `f"{len(stops)} заказ(а)"`.
Заменил её на `i18n_t("ru", "log.route_built", count=len(stops), ...)`
— лента событий доставки остаётся русской на этом этапе (решение по
`§3` ниже), но теперь через тот же механизм, что и будущий перевод
интерфейса, а не отдельным хардкодом. Проверено запуском: маршрут из
одного заказа даёт «1 заказ», не «1 заказ(а)» (см. §5).

Важная грабля, на которую наткнулся и исправил: назвал импорт функции
`t`, как и в остальном коде принято короткие имена — но в `delivery.py`
имя `t` уже используется как локальная переменная (накопитель времени
в циклах построения маршрута и ИИ-прогноза, `t = now + 4.0` и т.п.).
Python делает имя локальным для всей функции при любом присваивании —
импортированная `t` оказывалась не той `t`, и вызов падал с `'float'
object is not callable`. Решение — `from .i18n import t as i18n_t`.

## 2. Выбор языка на сервере — `webapp/server.py`

Параметр `?lang=ru|ro|en`, функция `_lang()` = `normalize_lang(request
.args.get("lang"))`. **Осознанно не стал добавлять чтение
`Accept-Language`**: проект — демо-стенд (см. `CLAUDE.md`,
`docs/HANDOFF.md`), выбор языка через `?lang=` явный и повторяемый по
прямой ссылке — это важно для скриншотов/проверок «покажи чек на всех
трёх языках»; автоопределение по заголовку браузера добавило бы ещё
один источник расхождения между тем, что видит проверяющий, и тем, что
видит браузер конкретного пользователя, без реальной пользы на этом
этапе (в системе пока нет пользовательских профилей/настроек, которые
можно было бы привязать к языку долговременно). Если появится
персистентный выбор языка (профиль сотрудника/покупателя) —
`Accept-Language` можно добавить как источник дефолта для `?lang=`
позже, это не ломает контракт.

## 3. Отдача каталога в браузер

Полное решение — на следующем этапе (270 строк JS в `<script>` внутри
`delivery.html`/`instore.html`/`game*.html` пока не переводятся, как и
просили). Но механизм должен *существовать и быть доказан* — сделал так:

* `i18n.client_catalog(lang, keys)` — берёт только запрошенные ключи
  каталога (не весь `MESSAGES`) и возвращает `{key: перевод}`. Не тащим
  в браузер каталог целиком заранее — сейчас клиентскому JS чека нужна
  всего одна строка (кнопка печати).
* `server.py::receipt_page` кладёт `client_catalog(lang,
  _RECEIPT_JS_KEYS)` в контекст шаблона как `i18n_json`.
* `receipt.html` встраивает его как `<script type="application/json"
  id="i18n-data">{{ i18n_json | tojson }}</script>` и маленьким JS
  читает `JSON.parse(...)`, подставляя текст кнопки печати через
  `textContent` — то есть тем же способом, каким сейчас в шаблонах
  делаются «голые» `textContent = "…"`. Проверено в браузере (Playwright
  MCP): на `?lang=ro` кнопка показывает «🖨 Tipărire bon», подставленный
  именно JS-кодом, а не Jinja-переменной напрямую — значит путь «сервер
  → JSON → JS» рабочий и его можно тиражировать на остальные шаблоны.

Когда дойдёт очередь до остальных ~270 строк: тот же `client_catalog`
можно расширить списком ключей на шаблон и вставить один раз в
`<head>` — переписывать сам JS (искать `textContent = "..."` и заменять
на `I18N['key']`) придётся построчно, это и есть следующий этап.

## 4. Фискальный чек Молдовы (bon fiscal, HG 141/2019)

Файлы: `webapp/delivery.py` (`_fiscal_receipt`, константы вверху файла),
`webapp/templates/receipt.html`, `webapp/server.py` (`receipt_page`).

**Убрано:** ФН/ФД/ФП, QR-строка `t=&s=&fn=&i=&fp=&n=1`, заголовок
«КАССОВЫЙ ЧЕК · ПРИХОД». QR-плейсхолдер (визуальный квадрат-заглушка,
не настоящий QR ни в старой, ни в новой версии) оставлен как есть —
это просто декоративный элемент чека, в задаче не было отдельного
требования по QR для Молдовы, и придумывать формат QR-строки без
источника не стал.

**Добавлено (по списку из задачи, один в один):**

| Реквизит | Поле | Пример |
|---|---|---|
| наименование налогоплательщика | `company_name` | `SRL "Gurman Retail"` |
| IDNO (13 цифр) | `idno` | `1003600123456` |
| адрес подразделения | `subdivision_address` (сервер) | `Chișinău, «Гурман» №21 · Ботаника` |
| заводской № ECC | `ecc_serial` | `ECC-CLD-271931` |
| рег. № ECC (SFS) | `ecc_reg` | `SFS-00417-1002` |
| № чека | `r.id` | `FD-00001` |
| наименование товара | `it.name` | — |
| стоимость + код ставки TVA по позиции | `it.qty*it.price` + `TVA {it.vat_rate}%` | — |
| итоги TVA по каждой ставке | `vat_breakdown` → `vat_lines` | `Total TVA 8% (...)`, `Total TVA 20% (...)` |

Решения, которых не было в явном ТЗ и пришлось принять самому:

* **Юрлицо — `SRL "Gurman Retail"` латиницей на всех трёх языках.**
  Официальное название при регистрации юрлица в Молдове не меняется по
  языку интерфейса чека (это не то же самое, что переводимые подписи);
  «ООО» — российская форма, для Молдовы неверна в принципе, выбрал
  `SRL`. Название бренда `Gurman`/«Гурман» не переводил — совпадает с
  правилом задачи «товары и категории не переводить», распространил его
  и на название сети.
* **IDNO и номера ECC — константы/детерминированный демо-формат**,
  так как в модели сети (`network.py`) нет отдельного поля с
  фискальными реквизитами кассы — их не было и для ФН/ФД/ФП в старой
  версии (там тоже был `rng.randint`). Серийный/рег. номер ECC различаются
  по типу кассы курьера (`android` — облачная касса, `smartpos` —
  терминал со встроенным ECC), это сохраняет прежнее архитектурное
  деление (`_ECC_BY_APP`, было `fn`-префиксы по `app`).
* **Адрес подразделения** — в модели сети нет отдельного поля «улица
  магазина», только `title` вида `«Гурман» №21 · Ботаника` (уже несёт
  локацию) и `lat/lon`. Собрал адрес как `{город}, {title магазина}` —
  город переводится (`city.chisinau`), название магазина не переводится
  (решение владельца: данные сети — как есть). Если модели сети позже
  добавят настоящий почтовый адрес, эту склейку в
  `server.py::receipt_page` заменить на прямое поле — тривиально.
* **Код ставки TVA на позицию** — вывел как `TVA {rate}%` прямо под
  строкой товара, а не отдельной буквенной кодировкой (в реальных
  молдавских чеках иногда встречаются буквенные коды A/B/C, но их
  точное соответствие ставкам не было в задаче и не проверялось мной —
  чтобы не выдумывать недостоверные официальные обозначения, вывел
  ставку в явном виде: это и есть код ставки — по нему однозначно
  видно, к какой строке итога TVA относится позиция).
* **НДС считается «изнутри» цены** (розничная цена в каталоге и так
  конечная, как было и раньше без TVA вовсе): `база = сумма/(1+ставка)`,
  `TVA = сумма − база`, округление — на уровне суммы по ставке, не по
  позиции (иначе накапливалась бы ошибка округления на чеках с 4-5
  позициями одной ставки).
* **`print_way`** — теперь строится один раз через
  `i18n_t("ru", "receipt.print_way.<app>")` в `_fiscal_receipt` (лента
  событий, всегда по-русски) и через `t(lang, "receipt.print_way.<app>")`
  в `server.py::receipt_page` (сам чек, на языке `?lang=`) — единственный
  источник фразы — ключ каталога, а не две захардкоженные строки, как
  было раньше (риск расхождения, который и был явно назван в задаче).

**Ставки TVA**: `VAT_STANDARD=20`, `VAT_REDUCED=8`,
`VAT_REDUCED_CATEGORIES={"Молочные продукты"}` — категория проверяется
по `product.category`, которую теперь несёт каждая позиция заказа
(`item["category"]`, добавил при сборке заказа в `_spawn_order`, иначе
на момент чека категорию взять было неоткуда без повторного похода в
`Store`).

## 5. Проверка — фактический вывод

Сервер поднят так, как указано в задаче (только `nohup ... &` — на
macOS нет `setsid`, деталь из §4.1 HANDOFF про `pkill`/`fuser`
актуальна, про `setsid` уточнение: отсутствует на macOS, использован
`nohup ... & disown`).

```
Сеть магазинов: 6 точек, эмуляция запущена
Мониторинг Zabbix: эмуляция (задайте ZABBIX_URL и ZABBIX_TOKEN для реального)
Карта: http://127.0.0.1:8050/
```

Первый чек появился раньше минуты (эмуляция заказов/сборки ускорена):

```
чеков: 1
id: FD-00001
```

Три языка + неизвестный код (`curl -o /dev/null -w "%{http_code}"` и
заголовок `<title>`):


Поиск остатков 54-ФЗ (`ФН|ФД|ФП|fn=|t=&s=`) по всем трём отданным
страницам — ничего не найдено (`no 54-FZ remnants found`).

Визуальная проверка (Playwright MCP, `?lang=ro`, скриншот и
`get_page_text`): чек отрисовался целиком — фирма, IDNO, адрес
подразделения, № ECC (заводской и SFS), позиции с `TVA 8%`/`TVA 20%`,
итоги по ставкам, TOTAL 642.00 L, способ выдачи чека курьером. Кнопка
печати — «🖨 Tipărire bon», причём подпись подставлена клиентским JS
из встроенного JSON-каталога (`I18N['receipt.print_button']`), а не
Jinja-переменной напрямую — доказывает путь «сервер → JSON → браузер»
из §3.

Плюрализация на живом логе: маршрут из одного заказа дал `1 заказ` (не
«1 заказ(а)») —

```
🗺 Маршрут R-005: 1 заказ из «Гурман» №3 · Измаил → Курьер Алексей (📱 Android (облачная касса))
```

Сервер остановлен по PID (`kill $(lsof -t -iTCP:8050 -sTCP:LISTEN)`),
порт свободен.

## 6. Что осталось непереведённым (следующий этап)

* ~270 строк клиентского JS в `delivery.html`, `instore.html`,
  `game.html`, `game_multi.html`, `map.html`, `fuel.html` и др. —
  голые русские литералы/`textContent`, каталог `i18n.py` под них ещё
  не наполнен (сейчас там только ключи, нужные чеку и одной фразе лога).
* Лента событий доставки (`_log(...)`) — вся русская, кроме того что
  теперь строится через `i18n_t("ru", ...)`; переключение ленты на язык
  запроса не делал (у ленты нет понятия «язык запроса» — она общая для
  всех клиентов `/api/delivery/state`, это отдельное архитектурное
  решение на будущее: либо переводить на клиенте по ключу события,
  либо оставить ленту диспетчерской и русской).
* Топливный контур, тренажёр, планограммы, документация — по прямому
  указанию задачи не трогались.
* Буквенные коды ставок TVA (если у SFS есть официальный стандарт
  A/B/C) — не проверял, вывел ставку явным числом (см. §4).
